# 字级 Transformer 重打分：评测（2026-09-08）

## 做了什么

- 模型：两档字级 decoder，small 23M、base 36M / 上下文 256，语料为中文维基 + LCCC（训练细节不在本仓库）。
- 推理：`crates/qingjian-neural`（candle），与训练脚本的 Python 打分对拍一致。M1 上 Metal 后端最快：空前文单条 6 ms，
  64 字前文 × 8 条 133 ms；CPU（Accelerate）约慢一倍，candle 自带 gemm 再慢一倍。按 token 算吞吐很低，是每层十几个小算子的调度开销在主导。
- 接法：Core `sentence::convert_paths` 出 Viterbi 前 6 条路径，`Engine` 按 `路径分 + λ·(神经分 − 静态二元分)` 重排，
  神经分只替换静态二元的判断，个人 n-gram、用户加分、敲错代价原样保留（早先试过 `(1 − λ)·路径分 + λ·神经分` 的线性混分，
  λ 0.5 时个人计数被稀释得厉害）。前文是本会话最近上屏的 64 个字符。只有 CLI `--neural` 接它。

## 明细说明回放这把尺子在整句上量不准

最好的一档（静态 λ 0.25 前文 64）逐条对账：变差 43 条、变好 45 条。变差里一大批是**模型对、日志错**：
`shurukuang` 日志选了 输入狂、模型给 输入框；`tiaoshi` 条是 → 调试；`gengkuai` 更会 → 更快；`jiaohu` 叫和 → 交互；
`siyou` 死有 → 私有；`zuoyong` 做用 → 作用；`hade` 哈的 → 好的。日志里「选了」的整句多半是当时按空格接受的基线自己的输出，
误选也照记，所以基线在整句上天然占便宜。真正模型错的：我的 → 沃德 ×4（云端学来的错读音用户词），资料 → 字了，才对 → 猜对。
变好的是 候选框 ×4、我之前 ×2、实际 ×2、不显示 ×2、增量、实现、下载、本地、目录、资源库、重写、进度 这类实词。

还有 全绿 → 全旅 ×3、服务商 → 服务上 ×2、技术面试 → 及书面是 这类模型没见过的搭配。

## 进壳（2026-09-08 晚）

1. **前文 KV 缓存**（`qingjian-neural::PrefixCache`）：前文在一次组句里不变，每层的 K / V 算一次存下来；每条候选只算「前文最后一个 token + 候选」这一小段，
   前文缓存部分不含最后一个 token，它的输出分布正好给候选第一个字用。Metal 上 64 字前文 × 8 条 133 → 28 ms，空前文 8 条 20 ms；
   剩下的是每层十几个小算子的调度开销，CPU（candle gemm）同样的活要 73 ms，还是 Metal。与 Python 对拍不变。
2. **Core 异步重排**（`engine/rescoring/`）：一次查询里整句转换会跑好几遍（纠错变体、中英混输比分），所有路径文本进一张「前文 + 文本 → 神经分」缓存；
   同步打分器当场补分（评测每句 69 → 27 ms），异步的先记下缺分的文本，壳停键后 `request_rescoring` 一次送后台线程（几条攒一批），
   `poll_rescoring` 收到后再 `query` 一次就全在缓存里。CLI `--neural-async` 走同一条路，300 句上与同步结果逐句一致。
3. **壳**：知微模型随包放 `Resources/models/hanzhang-zhiwei/`（56 MB fp16），后台线程加载 + 预热后接上；每键先读应用光标前 64 字当前文（应用给不出退回本会话历史），
   停键 80 ms 请求、20 ms 轮询，结果到了只重画当前页，翻过页或动过高亮不打扰。`[model] enabled` 开关在「云服务」页。
   TextEdit 端到端：`houxuanshengcheng` 候选声称 → 候选生成，`shururizhi` 输入日至 → 输入日志。
4. **只认最新那次请求的结果**（2026-10-16）：打字比模型快时，上一段按键的结果会比这一段的先回来。`poll_rescoring` 以前收到任何结果都返回 `true`，
   壳当成这一轮已经拿到、停了轮询，晚几十毫秒到的这一段整句（尤其是含章·通变直接生成的那条）就没人取，空格上屏的还是旧首选。
   MacBook 上的 TextEdit 端到端里 `firefoxliulanqi` 上屏成「覅」（生成结果 81 ms 就回来了，候选窗之后三秒没重画）；
   每段 80 ms 一个键、正好等于防抖时间，真人打字的节奏也会撞上。现在每次请求带序号，旧请求的结果照样进缓存，只有最新那次的到了才返回 `true`。

## 结论与下一步

模型有信息、接法成立，**在不带日志偏差的尺子上过了「整句 +2 个点」的门槛**（+4.3）。回放上看到的「整句变差」是尺子的问题。下一步按顺序：

1. 延迟已解决到能进壳（上一节）；再往下是算子合并或量化，以及模型后台加载的 12 秒（首次 Metal 编译）。
2. 应用上下文已接：IMK 的 surrounding text 当前文，评测集里的「上文」就是它的模拟。
3. 数据：语料里没有技术文本，`输入框`、`候选框`、`全绿`、`服务商` 这类词靠个人微调补；闲时训练那一步才是「越用越像自己」的来源。
4. λ 缺省已从 0.25 提到 0.5（0.75 最高但与 0.5 只差 0.3 个点，留点余量给个人 n-gram）。
5. 发版：数据包要带模型，权重许可另定。

## 2026-09-24 换 P2C 之后：两个 bug、一个架构上限

整句重排从含章·知微（字级模型）换成含章·通变（P2C，`crates/qingjian-neural::P2cScorer`）之后在冻结集上是 42.5% / 字准 79.3%，
但日常打字里中英混输整个坏掉：`woxiangxuexirust` 出 我想学习如斯。下面三件事是一次查出来的。

### 一、神经分不能写回 `Conversion::score`

P2C 打的是 `log P(汉字 | 拼音)`，字级模型打的是 `log P(汉字)`。前者被拼音条件住，比静态二元分高十几二十 nat，
抬升还随句子长短与静态模型的偏好变化，**不是常数偏移**。原来的 `rescore_paths` 把 `路径分 + λ·(神经分 − 静态分)` 写回 `score`，
这个被抬高的分就漏进了两处跨读法的比较：

- `find_correction`：原样能转出的整句分 vs 纠正后的整句分。
- `mixed_beats_plain`：混输头段分 + 英文词概率 vs 整段按拼音读的分。

两处的门槛（`correction_cost`、`ENGLISH_SWITCH_PENALTY`）都是按静态尺度定的。实测 `woxiangxuexirust`：

| | 原样 | 纠正后 | 结果 |
| --- | --- | --- | --- |
| 无模型 | −33.83 | −36.18 | 不纠 |
| 字级 LM λ0.75 | −33.58 | −36.48 | 不纠 |
| P2C λ0.75 | −16.90 | −13.87 | 纠成 我想学习如斯 |

更根本的原因：按贝叶斯 `log P(汉字|拼音) = log P(拼音|汉字) + log P(汉字) − log P(拼音)`，
最后那项只在**同一串按键**下是常数，而这两处比较的两边按键本来就不同。所以 P2C 的分只在同一串按键内可比。

改法：`rescore_paths` 只排名次，`score` 原样不动。冻结集不变（42.5% / 79.3%），混输恢复。

### 二、长句只给一条整句候选太少

`convert_sentence_with` 内部已经算了 `RESCORE_PATHS` 条并重排好，却只取第一条。冻结集 2081 句（全集每 4 句取 1）上：

| | 首选 | 前三 | 前五 |
| --- | --- | --- | --- |
| 改前 | 42.3% | 42.4% | 42.4% |
| 改后（`SENTENCE_CANDIDATES = 3`） | 42.3% | **45.5%** | 45.5% |
| 试过 5 条 | 42.3% | 45.5% | 45.7% |
| 无模型、改后 | 38.0% | **43.2%** | 43.2% |

给 5 条只再多 0.2 个点却挤掉整页词级候选，定 3 条；四个音节以下不给备选（那几格留给词级候选更值）。
无模型时也涨说明这不依赖神经模型，`sentence_paths` 的 `want` 参数让拼写纠错那条路仍然只算一条（它对每个纠正候选都要转一次）。

**坑**：第一版把「第一条不合格就继续找下一条」写成了 `continue`，结果 `nihao` 的最优路径 你好 是单个词（不算句子）被跳过，
第二条 你号 顶上来插到词库词 你好 前面。第一条不合格必须整条不出。

### 三、重排这层架构本身是瓶颈

同一份 2081 句，P2C **自由生成**（`P2c::convert`，束宽 5，不经词图不经重排）对比产品的重排路径：

| | 首选 | 前三 / 前五 | 字准 |
| --- | --- | --- | --- |
| 词图 + P2C 重排 | 42.3% | 45.5% | 78.5% |
| P2C 自由生成 | **51.9%** | 前五 **73.5%** | **83.0%** |

逐句配对：两边都对 35.4%，**只有生成对 16.5%，只有重排对 6.9%**，都不对 41.1%（McNemar χ²=81.1）。
两条路是互补的，不是替代关系——重排那 6.9% 来自词库、个人学习、辅码、混输，生成给不了。

并起来能到哪：

- 首选并集上限 58.9%
- 重排前三 ∪ 生成前二（占 5 格）**68.2%**
- 重排前三 ∪ 生成前五（占 8 格）75.9%

评测集是本项目自己的中文文档抽的，与 P2C 的训练语料（wikipedia / LCCC / IndustryCorpus2）不重叠，不是记忆效应。

代价是延迟：生成是 `O(生成字数)` 次串行前向（同一份集合上平均 130～200 ms、最慢 2.4 s），
重排是一次批量前向（平均 62 ms）。这是结构差异不是调参旋钮，要进产品得先解决。

实验入口：`--eval-text <集> --eval-generate data/models/hanzhang-tongbian/hanzhang-tongbian-small.qjm [--eval-details out.jsonl]`。
