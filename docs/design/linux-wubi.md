# Linux 五笔与形码方案接入

日期：2026-11-05。状态：实现完成，本机验证与未覆盖环境见 [验证记录](../notes/linux-wubi.md)；计划见 [实现计划](../plan/linux-wubi-implementation.md)。

## 目标与范围

让 Linux 用户在「青简设置 → 输入」选择五笔（86），可以关闭拼音只用五笔，也可以保留拼音混输。
交付按可提交上游的标准准备：实现、自动化测试、可用环境的真实输入验证、安装资源与用户文档一起完成。

覆盖共用 Linux Server，以及 Fcitx5、Fcitx4、IBus 三个前端的既有协议链路。
随包只有已有的五笔 86；用户自定义形码方案、导入的五笔词库沿用共用平台层的格式与路径。
接入 `SchemeSlot` 时同时保持已有全拼、双拼、注音的行为，复用它对自定义双拼的支持，不另写一套方案加载逻辑。

不包含字根图、自绘候选窗、辅码、新的五笔版本、排序算法调整或其他 Linux 功能补齐。
不修改默认输入方案，不替换用户原有输入法，不自动启用五笔，不提交 Git commit 或创建 PR。

## 改动前的缺口

- Core 已有 `CodeScheme`、纯形码与拼音混输、`code_tops`、`commit_unique_code` 和对应测试。
- `qingjian-platform::scheme::SchemeSlot` 已负责加载方案、应用规则与纯形码时的拼音开关，Windows 已接入。
- Linux 启动与配置热加载目前分别设置内置双拼、注音，没有接入形码方案和 `set_phonetic`。
- Linux 字母路径直接调用 `Engine::push`，没有返回顶字与满码自动上屏产生的提交。
- Linux 安装资源清单只复制 sample、glossary、levels、emoji 与产品数据，没有复制 `assets/schemes`；当前锁定的产品数据包也没有该目录。
- 设置程序已有方案选择与资源查找逻辑，但 `Feature::Schemes` 的 Linux 支持状态是待实现。

## 方案选择

采用「Linux Server 接入已有共用能力」：方案发现、码表加载、候选排序、自动上屏判定继续归共用层；
Server 只管理方案生命周期并将 Core 返回的提交放入已有协议响应。

不采用在 Fcitx 插件里单独实现五笔：这样会让 IBus 与 Fcitx4 行为分叉，也违反平台壳不访问词库的约束。
也不只开放设置开关：没有码表安装、启动初始化和按键提交，开关可选不等于功能可用。

## 方案与配置生命周期

在 Linux Router 中保存一个 `SchemeSlot`，统一处理启动初始化和后续配置更新。
方案目录使用资源根目录下的 `assets/schemes`，用户方案与五笔词库使用共用 `code_schemes` 的既定目录规则。
避免把路径依赖于当前工作目录；从安装后的二进制、源码树和临时测试资源根启动都应能找到正确资源。

配置语义沿用现有平台：

- 形码为五笔 86、拼音关闭：纯五笔。
- 形码为五笔 86、拼音开启：拼音与形码混输，排序沿用 Core。
- 形码关闭：恢复所选拼音方案。
- 形码找不到或加载失败：按 `SchemeSlot` 已有语义记录错误，并在没有可用形码且拼音关闭时回退拼音，避免完全无法输入。
- 非法 TOML 保持上次有效配置；方案文件加载失败的行为不另行改变共用平台层。

复用现有轮询节流，在配置改变以及用户方案、方案码表、导入五笔词库增删改时刷新。
纳入五笔词库启停与方案自动上屏、顶字规则变更，未变化时利用已有加载缓存，不在每次按键时重新读取整张码表。
仅在方案选择或方案资源发生实际变化时，取消所有活动会话中尚未提交的组词、刷新候选并清理过时的异步结果。
不擅自提交旧编码，已经上屏的文字不受影响；其他配置变化不应无故清空组词。
具体清理顺序由实现者按现有会话结构决定，用多会话回归测试固定行为。

## 按键与上屏

参照 Windows 的 `push_letter` 编排：先由 `Engine::code_tops` 判断是否顶出当前候选，再输入字母，最后接收 `Engine::commit_unique_code`。
提交与新的预编辑可以在同一次响应里共存，沿用已有协议，不新增五笔专用消息。
顶字时提交当前高亮候选而不是重新取首选；自动上屏遵循 Core 的纯五笔、满码、唯一候选条件。

必须覆盖空格与数字选词、翻页与高亮、退格、回车原样提交、标点、取消、Shift 中英切换，
以及连续输入产生「上一词已提交、下一词仍组词」的情况。
混输下 `v`、`u`、`i` 等字母的普通输入和 Shift 特殊入口按 Core 既有能力判断，不能沿用全拼专用分支吞码。
私密输入与密码框、失焦、断连和重连继续服从各前端的既有约定，不在本功能中改变框架差异。

## 设置、资源与安装

复用已有输入页，不新建 Linux 专用页面。只有能力与测试接通后，才把 Linux 的形码与自定义方案支持状态改为可用。
字根图与辅码继续保持原有平台支持状态。

在 `apps/linux/scripts/files.py` 的共用资源清单中纳入 `assets/schemes`，保留描述文件、码表、来源说明与许可证。
同一份清单用于源码安装、tar.gz 与 deb/rpm 资源准备；样例安装也带五笔方案，因为它不依赖正式拼音数据包。
安装清单登记新增文件，保持重复安装、目标冲突拒绝、卸载保留用户数据等已有行为。
不修改产品数据锁定版本，不下载新的五笔码表，不引入额外依赖或新的运行时服务。

## 验证与交付门槛

按先针对性测试、再跨层验证的顺序进行；功能测试先建立失败证据，再实现。

1. Linux Server 单元与协议测试：纯五笔、混输、顶字、满码唯一与重码不自动提交、选词、标点与退格。
2. 方案生命周期测试：启动即生效、拼音和形码切换、配置错误、方案缺失、用户方案优先级、规则和词库热更新、多会话隔离。
3. 安装测试：临时 prefix 与私有 XDG 中验证资源与许可证存在、重复安装、卸载不删除个人方案；同时检查源码安装和发行包共用资源输出。
4. Fcitx5、Fcitx4 的 CTest，以及 IBus 对真实私有 daemon 的端到端测试：五笔候选、空格上屏、自动提交与新预编辑同时存在。
5. 当前 Ubuntu 24.04 桌面的真实 Fcitx5 输入验证：记录系统、框架版本、测试应用、输入编码与实际文本；自动化图形测试使用隔离配置与学习目录。
6. `cargo fmt --all --check`，相关 crate 的测试与 clippy，随后运行非 macOS workspace 的既有门禁；不为此功能修改 Windows 或 macOS 行为。

现有环境有 Fcitx5、IBus、Xvfb 与 D-Bus 工具；没有检测到 Fcitx4 开发包和 Docker。
实现时评估是否可补齐依赖运行 Fcitx4 测试，以及是否能构建 deb/rpm；不能执行的验证明确记录为未验证，不能用编译成功或 Server 测试替代真机验证。
若某个前端暴露出必须修改它自身的行为问题，先记录可复现证据，再做最小修复；没有真实环境就不声称该平台已验收。

用户侧说明同步 `docs/user/platforms/linux.md`、五笔使用页和必要的英文对应页；工程侧同步 Linux 安装说明、crate 实现记录和相关待办。
不修改 CHANGELOG，不自动发布。交付说明区分已经通过的验证与还需维护者补验的环境。

## 实现者可决定的细节

具体模块拆分、测试夹具和快照结构沿用现有 Rust/C++/Python 约定；不额外引入监控库。
优先只修改 Linux、设置能力表与直接相关文档；只有复用接口确实不足且已有测试证据时才最小化调整共用平台层。
默认在当前工作区内联执行，保留已有未跟踪的 `.gobby/`，不创建分支或工作树。
完成实现与验证后，再按用户意愿更新本机安装和输入方案，避免开发期间反复打断正在使用的输入法。
