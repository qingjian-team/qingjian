# 架构决定记录（ADR）

`design/` 下的文档回答「现在是什么样、为什么这么定」，是随代码一起演进的**现状说明**；
这里回答的是「当时在几个方案之间怎么选的」，是**带日期的决定**，写下来就不再改（后续变化写新的一条，
旧的那条标成「已被 NNNN 取代」）。

为什么要单独有一份：`design/` 的叙述会随实现漂移，读的人看不到被放弃的选项，于是每隔一两年就有人
把同一个问题重新提一遍（「为什么不直接用 egui / slint」「TSF 为什么要拆两个进程」「翻译为什么不做成
`Vec<Translation>`」）。ADR 的作用是把「当时已经权衡过、结论是这样」钉住，让翻案的人至少先看到代价。

## 什么时候写

- 动了跨 crate 的边界：分层、进程划分、数据所有权的归属
- 选了一个以后很难换的基础件：UI 引擎、序列化格式、模型推理方式、通信协议
- 否掉了一个看起来更省事的方案，而且这个方案以后还会被反复提起

日常改动、单个 crate 内部的实现选择不写 ADR（该写注释、`notes/` 或 PR 描述）。

## 格式

一条一个文件，`NNNN-短横线小写标题.md`，编号递增不复用。正文按下面五节写，宁短勿长（一般 40–80 行）：

```markdown
# NNNN 标题

- 状态：已采纳 / 已被 NNNN 取代 / 已废弃
- 日期：YYYY-MM-DD
- 相关：链接到 design/ 文档、PR、issue

## 背景
约束是什么：平台限制、性能预算、许可、人力。

## 备选
A / B / C 各是什么，当时看到的好处与代价。**被否掉的那些要写清楚为什么被否。**

## 决定
选了哪个，一句到三句。

## 后果
好的、坏的、因此必须一直守住的规则（这条最要紧：后面的人靠它判断能不能改）。

## 复审触发条件
什么情况下应该重新讨论这条决定。
```
