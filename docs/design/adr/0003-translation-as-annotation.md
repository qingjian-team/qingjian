# 0003 翻译是候选的 annotation，不是并列多语言

- 状态：已采纳
- 日期：2026-10（`docs/contributing.md` 的架构约束成形），本文件 2026-11-28 追记
- 相关：[../candidate-ui.md](../candidate-ui.md)、`crates/qingjian-translate`、`crates/qingjian-predict`、
  `crates/qingjian-core/src/candidate`

## 背景

青简在中文候选旁边显示一行译文（「学习语言」），用于把自己正在输入词的字面意思看到。产品上定的是
**一次只学一种语言**：用户在设置里选一个 Learning Language，候选上就只出现它。而技术上，候选是引擎每按键
都要重算一遍的数据，输入延迟预算以毫秒计，译文来自本地表（`Glossary`）、云兜底（`CloudGlossFiller`）与
模型（`qingjian-predict`），其中云端部分必然异步。

## 备选

**A. `Candidate.translations: Vec<Translation>` 或 `HashMap<Lang, String>`**：所有语言一次带上，界面自己挑。
否掉的原因不是性能，而是**产品原则会被数据结构吃掉**：一旦类型层面允许并列多语言，后续每一个界面、
每一处缓存、每一次学习都会顺手带上「多语言」的假设，最后「一次只学一种」就只剩下设置里那一行字。

**B. 译文在平台层查**：引擎只给词，壳自己查表。否掉：壳不许可访问词库与翻译（见
[../architecture.md](../architecture.md) 的约束），而且 Android / Linux 面板会各写一遍。

**C. 译文是候选的可选 annotation（当前）**：`Candidate.translation: Option<Translation>`，唯一一条；
查询异步、不阻塞候选返回，就绪后由引擎通知壳刷新。

## 决定

走 **C**。要点：

- 类型上是 `Option<Translation>`，**不是集合**——「只有一种」由类型保证，不靠约定
- 翻译查询不参与候选生成的临界路径：候选先返回，译文到了再补（`docs/design/candidate-ui.md` 的时序）
- 云端兜底与本地表叠在一起，仍然只产出一条
- 繁体输出是**候选文本**的变换，与 translation 是两件事，各自独立

## 后果

好的：

- 「一次只学一种语言」在 API 层面成立，实现者想违反也难
- 候选生成不被翻译拖慢；云端慢或断网时候选照常出
- 各平台的壳只画一条译文，视觉上不用处理并列排布

坏的 / 必须一直守住的：

- **不要为了「顺便支持多语言」把 `Option` 改成集合**。真要支持「同时看两种」，先改产品原则与这条 ADR，
  再改类型；顺序反了就是事故
- 译文的异步到达意味着壳要处理「同一条候选的两次渲染」，各平台的刷新路径必须幂等
- 学习语言切换时，已缓存的译文要整体失效，不能混用

## 复审触发条件

- 产品决定支持「双语对照」或「学习语言 + 母语对照」
- 译文来源从「一条最佳」变成「多个来源需要并列展示并让用户挑」
